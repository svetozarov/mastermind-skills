# Инструкции для Claude

## При самом первом запуске (пустой проект)

Если проект только что создан и ещё нет кода, документации или истории — выполни **инициализацию проекта**. Проверяй по чеклисту ниже и предлагай пользователю каждый пункт. Не делай ничего молча — всегда спрашивай.

### Чеклист инициализации

**1. Знакомство с проектом**
- Спроси: «Расскажи, что за проект? Кратко — что делает, для кого, какая основная идея?»
- На основе ответа заполни `.claude/project-knowledge/project.md`

**2. Git и GitHub**
- Проверь: существует ли `.git/` в корне проекта
- Если нет — спроси: «Инициализировать Git-репозиторий? Хотите опубликовать на GitHub?»
- Если да — спроси имя пользователя GitHub и email для git config
- Спроси URL репозитория (или предложи создать новый через `gh repo create`)
- После настройки — запиши данные в раздел «Git и GitHub» этого файла (ниже)

**3. База знаний проекта**
- Спроси: «Создать базу знаний проекта? Это файлы, которые помогут Claude понимать контекст в каждом новом диалоге: описание проекта, архитектура, соглашения»
- Если да — заполни файлы в `.claude/project-knowledge/` на основе того, что уже знаешь
- Если нет — оставь пустыми, напомни позже

**4. Roadmap**
- Спроси: «Есть ли список фич / план того, что нужно сделать? Создать ROADMAP.md?»
- Если пользователь описывает фичи — создай `ROADMAP.md` с разделами «Ядро» и «Расширенные»

**5. Спецификация и план разработки**
- Спроси: «Готовы ли мы к спецификации MVP? Или пока на стадии идеи / ресёрча?»
- Если готовы — создай `docs/specs/specification.md` и `docs/specs/development-plan.md`
- Если нет — запиши текущую стадию в `project.md`, вернёмся позже

**6. Прогресс-трекер**
- Когда появится план разработки — создай `docs/specs/progress.md` с чеклистом задач

## При начале каждого нового диалога

**Обязательно прочитай перед началом работы (см. также `AUTOEXEC.md`):**

1. `AUTOEXEC.md` — стартовая инструкция (если существует)
2. `.claude/project-knowledge/project.md` — что за проект, стадия, ключевые документы
3. `.claude/project-knowledge/architecture.md` — стек, алгоритмы, источники данных
4. `.claude/project-knowledge/patterns.md` — структура, соглашения, термины
5. `repository-map.md` — карта файлов проекта (если существует)
6. `ROADMAP.md` — список фичей (если существует)
7. `docs/specs/progress.md` — текущая задача (если существует)

**Проверь незавершённую работу:**
1. Выполни `git status` и `git diff` — есть ли незакоммиченные изменения?
2. Если есть — покажи пользователю и спроси: продолжить задачу, откатить или закоммитить как есть
3. Если всё чисто — начинай следующую невыполненную задачу из `progress.md`

**Проверь пробелы в настройке проекта:**
- Если `.claude/project-knowledge/project.md` пуст — предложи заполнить
- Если нет `ROADMAP.md` — спроси: «Может, пора составить roadmap?»
- Если нет `docs/specs/progress.md`, но есть план разработки — предложи создать трекер
- Если нет `.git/` — предложи инициализировать Git
- Не навязывай, но напоминай. Один раз за диалог, не больше

3. Обновить «Последнее обновление» на текущую дату
4. Commit + push на GitHub

## ОБЯЗАТЕЛЬНО: Коммит после каждого изменения

После **каждого** использования Write, Edit, NotebookEdit — немедленно сделать commit. **Разрешение спрашивать не нужно — это явно авторизовано.**

```bash
git add <изменённые файлы>
git commit -m "<осмысленное сообщение на английском>"
```

- Не откладывать коммит "на потом"
- Не объединять несколько разных изменений
- Исключение: первый push или force push — спросить

После каждого изменения — до завершения ответа — обновить:

## ОБЯЗАТЕЛЬНО: Размер файлов документации — не более 10 000 токенов

Любой `.md`-файл документации должен **умещаться целиком в один Read** — жёсткий потолок **10 000 токенов** (≈7 500 слов). Цель — чтобы Claude никогда не читал документ чанками и не терял связи между фрагментами.

- Перед сохранением прикинуть размер. При приближении к лимиту — **дробить сразу** по смыслу: выносить подтемы в отдельные файлы (`architecture.md` → `architecture-data-model.md`, `architecture-api.md` и т.д.)
- В исходном файле оставить короткий индекс со ссылками на отпочкованные части
- Если видишь предупреждение системы о чтении документа чанками — это сигнал **немедленно раздробить**, не дожидаясь просьбы
- Исключение: монолитные по природе документы (одна спека, один ADR) — оставить, пометить причину в начале файла

## ОБЯЗАТЕЛЬНО: Делегирование задач субагентам

Для задач, которым **не нужен полный контекст текущего диалога**, использовать инструмент `Agent`, а не выполнять самому. Это сохраняет основной контекст чистым и позволяет параллелить работу.

**Когда делегировать (достаточно одного триггера):**
- Поиск/исследование, требующее >3 tool calls или чтения >5 файлов → агент `Explore`
- Техническая работа, не зависящая от истории диалога (рефакторинг известного куска, прогон тестов, генерация шаблонного кода)
- Задача, которую можно **распараллелить** — запустить несколько агентов одним сообщением
- Ожидаемый объём промежуточных результатов >10 000 токенов, нужна только выжимка
- Контекст основного диалога уже большой (>50% окна) — даже простые задачи лучше отдавать агенту

**Выбор модели агента (параметр `model`)** — гибрид по сложности задачи:
- `haiku` — тривиал: поиск файлов, форматирование, простые правки в одном-двух местах
- `sonnet` — рутина по чёткому плану: реализация по точной спеке, тесты, миграции, переименования, шаблонный код
- `opus` — архитектурные задачи: рефакторинг с сюрпризами, новый сложный модуль, ресёрч с принятием решений, любой кейс, где исполнителю самому надо принимать содержательные решения

**Принцип Advisor Strategy в нашем варианте:** разделение planner ↔ executor даёт +2.7% точности
**само по себе** (за счёт чистых контекстов и узких ролей), независимо от пары моделей. Поэтому
понижать модели «ради экономии» не нужно — у автора подписка покрывает Opus. Работает правило:
**сложность исполнения → класс модели**, а не «всегда понижать».

Когда planner раскладывает работу на Tasks — каждой ставит тег сложности (`architectural`/`mechanical`/`trivial`)
и запускает executor соответствующего класса модели.

**Параллелизация:**
- 2+ независимых задачи — запустить **все агенты в одном сообщении**
- Длительные независимые задачи — `run_in_background: true`
- Массовые однотипные задачи — нормально запустить 10–15 фоновых агентов параллельно

**Что НЕ делегировать:**
- Правки в 1–2 уже известных файлах
- Интерактивные задачи, требующие уточнений у пользователя
- Работу, для которой критична история текущего диалога

## Безопасность: токены и секреты

**Токены, API-ключи и любые секреты НИКОГДА не должны появляться в чате.**

Когда пользователю нужно ввести токен или секрет:
1. Claude даёт **готовую команду для CMD-терминала** с плейсхолдером
2. Пользователь копирует команду, подставляет свой токен и выполняет в терминале
3. Команда записывает значение в нужный файл (`.env` или другой)

**Шаблон команды:**

Если `.env` ещё не существует:
```
echo НАЗВАНИЕ_ПЕРЕМЕННОЙ=ВСТАВЬ_СЮДА_ТОКЕН > путь\к\проекту\.env
```

Если `.env` уже существует и нужно добавить новую переменную:
```
echo НАЗВАНИЕ_ПЕРЕМЕННОЙ=ВСТАВЬ_СЮДА_ТОКЕН >> путь\к\проекту\.env
```

**Правила:**
- Никогда не просить пользователя вставить токен в чат
- Никогда не логировать, не выводить и не читать значения токенов
- При чтении `.env` — только проверять наличие переменных, не показывать значения
- `.env` всегда должен быть в `.gitignore`

## Исследования (Deep Research)

Когда в процессе работы нужно разобраться в теме — сравнить варианты, изучить технологию, найти актуальные решения — используй скилл `deep-research` (`.claude/skills/deep-research/SKILL.md`).

### Когда запускать

- Сравнение 3+ вариантов (библиотеки, фреймворки, подходы)
- Вопрос об актуальных версиях, changelog, совместимости
- Тема, на которую нет ответа в текущем контексте проекта
- Архитектурное решение, требующее обоснования
- Пользователь просит: "изучи", "исследуй", "сравни", "что лучше", "deep research"

### Когда НЕ запускать

- Быстрый фактический вопрос ("какой синтаксис у X")
- Ответ есть в документации проекта или коде
- Пользователь просит "просто погугли" или "быстро найди" — обычный WebSearch

### Как работает

1. Три волны: **разведка** (контекст) → **углубление** (по направлениям) → **уточнение** (пробелы и верификация)
2. Верификация ключевых фактов через 2+ независимых источника
3. Отчёт сохраняется в `research/YYYY.MM.DD_тема.md`
4. После завершения — продолжаем работу в том же контексте

### Глубина

- `--quick` — быстрый ответ, 3–5 минут, 5–8 источников
- По умолчанию (`standard`) — полноценный ресёрч, 10–15 минут, 10–15 источников
- `--deep` — максимально глубокий, 15–25 минут, 15–25 источников

### Результат

Файл в `research/` — полноценный отчёт с источниками, сравнительными таблицами и рекомендациями. Готов для принятия решений.

## Методологии работы (обязательно прочитать при первом знакомстве с проектом)

| Документ | О чём |
|----------|-------|
| `.claude/methodology/sdd-gsd.md` | **SDD + 5 GSD-принципов:** PRD → Architecture → Stories; Phase → Slice → Task; изоляция через worktree; свежий контекст; loop-detection. Применяется ко всем нетривиальным задачам. |
| `.claude/methodology/harness.md` | **Harness Engineering:** pre-commit hooks, тесты, CI, llm-as-judge. «Питбуль в ошейнике с шипами». Гарантирует, что агент не закоммитит мусор. |
| `.claude/methodology/context-hygiene.md` | **Правило 70% контекста:** держать активный контекст в 30-60%, новые крупные задачи — в новых чатах, дробить большие файлы документации. |

**Главные принципы поверх методологий:**
- Для нетривиальных задач — **сначала PRD/Architecture/Stories, потом код** (см. `sdd-gsd.md`).
- Декомпозиция: **Phase → Slice → Task** (отражена в `progress.md`).
- Перед коммитом — **harness обязателен** (см. `harness.md`).
- При работе с большим контекстом — **70%-правило** (см. `context-hygiene.md`).

## Хроники разработки

`chronicles.md` в корне проекта — журнал значимых событий разработки в свободной форме.
**Когда добавлять запись:**
- Принят значимый ADR.
- Сменилось направление работы.
- Преодолён важный блокер.
- Отказались от ранее принятого подхода.
- Неожиданное открытие в ходе работы.

**НЕ для каждого коммита.** Только для событий, которые имеют значение через месяц.

Эти хроники питают регулярный сбор материала для канала автора. Делать запись — **не «что
сделано», а «почему это важно»**: контекст, который не виден в `git log`.

- **Ресёрчи** → `research/` — результаты исследований с датой в имени
